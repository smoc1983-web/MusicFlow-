### Что уже сделано правильно

Чёткие правила/политики уже вынесены из UI: `DownloadSizeEstimate`, `DownloadCleanupPolicy`, `CinemaAudioPickerPolicy`, `RadioQueuePolicy`, `CinemaScreenAwakePolicy`, `DownloadActionPolicy`. Для многих есть отдельные unit-тесты. Сохранить эти границы; не создавать поверх них лишние абстракции.

### Где пока недостаточно доказательств

- **module-cycle / tangle:** без полноценного графа Kotlin-символов и зависимостей не утверждать наличие циклов.
- **field-leak:** `internal` Kotlin и единый пакет — недостаточное основание объявить конкретное нарушение. Необходим конкретный граф чтения/записи состояния.
- **shallow-module:** длина файла или число функций сама по себе не определяет глубину модуля. Нужно сопоставление API и внутренних действий.
- **CRAP < 10, Dryer < 0.8, mutation:** соответствующие применимые к Kotlin инструменты не установлены и не запускались. **Статус: NOT CHECKED**, а не PASS.
- Нельзя оценить воспроизведение в реальной сети или сохранение файлов только по прочитанному исходнику и unit-тестам.

1. **Закончить и сохранить текущую TEST 0.7.61**, не вмешиваясь архитектурной перестройкой в её `app/` и подпись. Убедиться в независимых обязательных UI/DASH и unit gate; внешнее DNS-фейл окружения записывать отдельно, не как PASS источников.
2. **В отдельной audit/refactor ветке** подключить Kotlin-совместимый Detekt (первоначально `report-only`, без подавления реальных критических ошибок), отдельно `lintDebug`, собрать объективный baseline по сложности, long-method, class/function count. Переводить проверки в blocking только после настройки и исправления обнаруженных ошибок. `deslop-please` Rust бинарник не подключать.
3. Добавить Kotlin-тесты архитектурного направления зависимостей (или эквивалент по PSI): `ui -> domain -> data/platform` и запрет зависимости `domain -> Compose/Activity/Media3` для выделяемых *чистых* правил. Пока пакеты плоские — внедрять правило постепенно, не объявлять несуществующих циклов.

## Критерии завершения следующего этапа

- Отдельная ветка и baseline Detekt + фактически выполненный `lintDebug`; ссылки на Actions run и вывод сохранены в журнале.
- Есть измеримый граф зависимостей или архитектурные тесты: отсутствие новых нарушений на изменённых файлах; старые проблемы не замаскированы массовыми исключениями.
- Ровно один выбранный срез выделен с сохранением API и воспроизводимыми тестами поведения до/после.
- User-facing TEST и официальный `main` не меняются без осознанного релизного решения. Аудит **не даёт разрешения** на публикацию новой версии.

**Итог:** механический запуск `deslop-please` к этому Kotlin-проекту неприменим; показания выше — подтверждённые метрики и архитектурные кандидаты, но не ложный автоматический lint verdict.
