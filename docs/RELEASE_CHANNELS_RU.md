# MusicFlow — постоянный порядок выпуска основной и тестовой версий

**Каноническая инструкция для следующих чатов и автоматических агентов.** Перед началом релиза читать `AGENTS.md`, `DEVELOPMENT_JOURNAL.md`, этот файл и реальное состояние `main`, GitHub Actions и GitHub Releases. Все фактические действия и проверки сразу заносить в журнал. Не считать публикацию или установку успешной без доказательств.

## 1. Два изолированных канала

| Свойство | Основной (official) | Тестовый (TEST) |
|---|---|---|
| Исходная ветка | `main` после успешной проверки/merge | отдельная `feature/*` или `test/*`; не публиковать тест как official |
| Имя пакета | **`com.musicflow.preview`**, без суффикса | **отдельный** applicationId: для debug по умолчанию `com.musicflow.preview.dev`; у конкретных тестов, например, `com.musicflow.preview.radioarttest50`; проверять реальный манифест каждого APK |
| Подпись | **только оригинальный постоянный MusicFlow JKS** | отдельный стабильный тестовый/debug ключ; никогда не подменять официальный сертификат |
| SHA-256 сертификата | `c461ee635d5b295ef6c765e1ae533d0079dc6e53cb2632a11a1b445773752410` | отличен от официального; должен сохраняться между обновлениями **одной** тестовой установки |
| GitHub Release | строго числовой тег `vX.Y.Z`, **не** prerelease/draft | тег с `-test`, `-preview` или назначением, обязательно `--prerelease` |
| Файл APK | строго **`MusicFlow_X.Y.Z.apk`** | отдельное имя с `TEST`, например `MusicFlow-RadioArtwork-TEST-0.7.50.apk` |
| Обновлятор | обновление предлагается в основном приложении; проверяет пакет и сертификат | собственный тестовый канал / отдельная установка; **не** попадает в официальный обновлятор |

**Критически важно:** Android устанавливает обновление поверх текущего приложения только при совпадении `applicationId`, совместимой подписи и большем `versionCode`. Основной APK никогда не подписывать debug/test ключом. Нельзя «починить» несовпадение подписи простым переименованием APK. Основную установленную версию не удалять: это может удалить данные.

## 2. Проверенный выпуск основного приложения

1. Прочитать последние записи `DEVELOPMENT_JOURNAL.md`, `AGENTS.md`, исходники, текущее `app/build.gradle.kts`, последнее официальное `vX.Y.Z` и результаты CI. Повышать `versionName` и `versionCode`; для существующего соглашения `versionCode = major*10000 + minor*100 + patch` (например, `0.7.52 -> 752`). Сохранить `applicationId = "com.musicflow.preview"`.
2. Исправлять код в рабочей ветке; следовать `ub-mode`; запускать `:app:testDebugUnitTest :app:assembleRelease`. Записать ссылку на **успешный** Actions run, commit SHA, ID артефакта неподписанного APK и его SHA-256. Проверять, что тестовый APK не содержит другого package/version. После тестов объединить в `main`. Проверить отсутствие отличий `app/` от собранного источника, если подписанный APK создаётся из артефакта рабочей ветки.
3. **Обычный путь**: `.github/workflows/release-signed-musicflow.yml` запускается автоматически на `main`, выполняет Kotlin-тесты, восстанавливает оригинальный JKS из зашифрованной копии и публикует новую официальную версию. Для этого в GitHub Actions Secrets должны быть `MUSICFLOW_SIGNING_BACKUP_PASSPHRASE`, `MUSICFLOW_SIGNING_STORE_PASSWORD`, `MUSICFLOW_SIGNING_KEY_ALIAS=musicflow`, `MUSICFLOW_SIGNING_KEY_PASSWORD`. Если секреты отсутствуют, workflow **преднамеренно останавливается** — не объявлять релиз готовым.
4. **Доказанный резервный путь при отсутствии Secrets (использован для 0.7.51 и 0.7.52)**: восстановить JKS **локально** из сохранённого владельцем оригинального ключа/личных материалов `MusicFlow_GitHub_Actions_Secrets.txt`, либо расшифровать `.github/signing/MusicFlow_signing_release.jks.enc.b64` с **отдельным** личным файлом `MusicFlow_backup_decryption_passphrase.txt`. JKS, пароли, незашифрованные ключи и личные материалы **не записывать в Git/issue/PR/логи**. Перед подписью проверить SHA-256 исходного JKS `ef67656ce219d51335bb90ec388fea2ab3632e865016196315ff50f67e7ef72c`, alias `musicflow` и сертификат выше. Подписать **точный, уже протестированный unsigned release APK**, используя `apksigner` с v2/v3; проверить `apksigner verify --verbose --print-certs`. Сверить `com.musicflow.preview` и правильные код/имя версии.
5. Для воспроизводимой публикации без копирования личного ключа на GitHub создать `zstd --patch-from=<unsigned.apk> <signed.apk> -o <patch.zst>`, дополнительно сжать patch (как в `.github/release-assets/v0752/`), локально реконструировать подписанный файл и проверить **полное байтовое совпадение** с оригинальным подписанным APK. В репозиторий допускаются лишь **не содержащий закрытого ключа** `signed-delta.doublezstd.b64`, `checksums.env` и workflow. Хранить SHA-256 unsigned, patch, outer, signed и исходный успешный run/commit.
6. Создать для **новой** версии guarded workflow по образцу `.github/workflows/publish-v0752-original-signed.yml`: загрузить точный GitHub Actions артефакт (например `gh run download <run-id> -n <artifact-name>`); проверить исходный run `success`, его commit SHA и отсутствие изменений `app/`; сверить все SHA; восстановить signed APK из patch; запустить `zipalign -c`, `apksigner verify`, `aapt dump badging`; проверить **оригинальный сертификат** и лишь затем `gh release create vX.Y.Z MusicFlow_X.Y.Z.apk SHA256SUMS.txt --latest`. **Для сравнения старого commit SHA обязателен `actions/checkout@v4` с `fetch-depth: 0`**: shallow checkout в 0.7.52 ложно выдавал «App sources changed since signed preflight».
7. Ни обычный, ни резервный путь **не должен перезаписывать существующий официальный тег/файл**. В случае ошибки — исправить причину, выполнить новый запуск и зафиксировать его ID. После `success` независимо проверить REST GitHub Release: `draft=false`, `prerelease=false`, правильный тег и APK, SHA-256 файла совпадает с локально подписанным, сертификат подтверждён логами. Затем проверить на устройстве: «О приложении → Проверить обновление», обновить **поверх** установленного приложения, проверить сохранение настроек и воспроизведение. Только фактически проверенные этапы отмечать как успешные.

## 3. Выпуск тестовой версии

1. Создать отдельную рабочую ветку, присвоить тестовой сборке **иной applicationId**, а также различимое имя приложения и `versionName` с test-суффиксом. Убедиться, что debug/release конфигурация теста **не использует оригинальный ключ основного приложения**. Стабильный тестовый ключ требуется только для обновления **тестовой** установки поверх предыдущего теста.
2. Выполнить JUnit и сборку, проверить пакет и `apksigner`, сохранить APK как `MusicFlow-<feature>-TEST-<version>.apk`. Пример реального процесса: `.github/workflows/musicflow-v0750-radio-artwork-test.yml`, пакет `com.musicflow.preview.radioarttest50`, тег `v0.7.50-radio-artwork-test`.
3. Сохранять тест как отдельный GitHub Release с `--prerelease`, **никогда** под чистым `vX.Y.Z` и **никогда** с именем файла `MusicFlow_X.Y.Z.apk`. Это обязательное правило после инцидента, когда тестовый 0.7.50 предлагался основному 0.7.49 и не устанавливался из-за несовпадения сертификата. Не переводить TEST в official простым переименованием.
4. Проверять тестовую установку отдельно от основной; сообщать о тестовых результатах, баг-репортах, сборках и коммитах в журнале. После подтверждения теста переносить нужные изменения кода в `main`, **повышать official версию и отдельно подписывать оригинальным JKS**, а не распространять тестовый APK как основной.

## 4. Не повторять прежние ошибки

- **0.7.50 TEST в основном обновляторе:** основной апдейтер теперь фильтрует `prerelease`/`draft`, требует тег `^v\d+\.\d+\.\d+$`, файл `MusicFlow_X.Y.Z.apk`, сравнивает подпись и пакет до установки. При каждом релизе проверять защитные unit tests.
- **0.7.51 и 0.7.52 при пустых Actions Secrets:** не тратить время на бесконечные ручные прогоны неизменённого `release-signed-musicflow.yml`; сразу проверить доступность резервного оригинального JKS и использовать проверенную схему signed-delta либо настроить Secrets.
- **0.7.52 первая попытка signed-delta:** `git diff <source> HEAD -- app/` падал на shallow checkout с ошибочным сообщением о различиях. Использовать `fetch-depth: 0`; различать ошибку истории Git от реального изменения исходников.
- **Старый `Build MusicFlow APK`:** legacy `scripts/verify_v0711.py` и `verify_v0712.py` содержали жёсткие требования к устаревшему номеру версии или точному layout. Не принимать их ошибки за подтверждение неисправного официального APK; исправлять устаревшие проверки отдельно, но не пропускать **актуальные JUnit, сборку и контроль подписи**.
- **Никаких вымышленных успехов**: подтверждение `assembleRelease` ещё не означает подписанного APK; публикация Release ещё не означает установку на смартфон. Всегда записывать точную стадию.
