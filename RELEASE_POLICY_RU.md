# MusicFlow — обязательный порядок обновлений

**Постоянное требование проекта:** пользователь должен получать и устанавливать новые версии непосредственно внутри MusicFlow, не переходя на GitHub для каждого обновления. Нельзя выдавать тестовый APK с иным package ID или случайной подписью за готовое обновление.

Контрольный пакет публичного канала: `com.musicflow.preview`.
Эталон подписи: та же, что у опубликованного APK v0.7.25; сертификат проверяется в CI. Приватный ключ хранить только в GitHub Actions secrets / защищённой резервной копии, никогда в репозитории.

Условия публикации релиза:

1. Увеличить `versionCode` и `versionName`; сохранить `applicationId`.
2. Собрать именно `assembleRelease` с прежним постоянным ключом, не `assembleDebug`.
3. Через `apksigner` проверить подпись и сравнить отпечаток с v0.7.25.
4. Через `aapt` проверить `packageName`, `versionCode`, `versionName`.
5. Опубликовать подписанный APK в **GitHub Releases** с тегом `v0.7.X`; только тогда встроенный updater увидит новый выпуск.
6. Проверить: приложение обнаруживает новую версию, скачивает APK, проверяет пакет/подпись и передаёт Android Installer без удаления данных. Скрытая установка без подтверждения Android не обещается.
7. Предпочтительно провести реальную установку поверх предыдущего релиза на тестовом устройстве; CI-проверки сертификата не заменяют её.

**Запрещено** публиковать debug APK `com.musicflow.preview.vktest` как апдейт `com.musicflow.preview`. Бинарник `.vktest` 0.7.26 был собран непостоянным debug-ключом и **не может быть обновлён** публичным релизом; для перехода на стабильный канал нужна одноразовая установка подписанного официального APK. Данные другого пакета не мигрируют автоматически, поэтому не обещать обратного.

Если секреты подписи отсутствуют, остановить публикацию и явно сообщить о блокировке. Не менять ключ самостоятельно ради выпуска.
